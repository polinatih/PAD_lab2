# Шпаргалка к защите

## Рассказ о проекте за 2 минуты

> Это сервис доставки еды «Ложка». Клиент выбирает ресторан, оформляет и оплачивает заказ, ресторан его готовит,
> курьер доставляет, а клиент может оставить отзыв.
>
> Backend разделён на **7 микросервисов** по зонам ответственности: auth (пользователи и JWT), restaurant (рестораны
> и меню), order (заказы), payment (оплата), delivery (курьеры), notification (уведомления), review (отзывы).
> **У каждого своя база данных** — 7 баз PostgreSQL, чужая база сервису недоступна.
>
> **Синхронно, по REST**, сервисы общаются только когда ответ нужен сразу — например, при оформлении заказа
> order-service спрашивает у restaurant-service актуальные цены, потому что ценам из браузера доверять нельзя.
> **Всё остальное — через RabbitMQ.** Заказ проходит через несколько сервисов как **saga**: заказ создан → оплата →
> ресторан готовит → курьер → доставлено. Если что-то идёт не так, срабатывают компенсации: нет оплаты — заказ
> отменяется, ресторан отказался — деньги возвращаются.
>
> Чтобы события не терялись, используется **transactional outbox**, а все обработчики идемпотентны.
> Снаружи доступен только **nginx-gateway**; каждый запрос получает **X-Request-ID**, по которому его можно проследить
> в логах всех сервисов, даже через очередь.

## Что показать вживую (5–7 минут)

Подготовка: `docker compose up -d --build`, затем `docker compose restart gateway`. Открыть три окна:
обычное (клиент), инкогнито (ресторан), второй браузер или профиль (курьер).

1. `docker compose ps` — 7 сервисов + postgres, rabbitmq, gateway в статусе healthy.
2. **Клиент** `client@demo.md` — каталог → «Бабушкины плачинты» → корзина → оформить.
3. **Оплата** картой `4000 0000 0000 0002` (отказ банка, «осталось попыток: 2»), затем `4242 4242 4242 4242`.
4. **Ресторан** `owner2@demo.md` — на доске появился заказ (и уведомление в колокольчике) → «Принять» → «Готово».
5. **Курьер** `courier@demo.md` — «На линии» → «Взять заказ» → «Забрал» → «Доставил».
   В окне клиента «чек» сам дошёл до «Доставлен», в колокольчике — все этапы.
6. **Отзыв** — 5 звёзд; в каталоге у ресторана появился рейтинг; ресторан отвечает на отзыв.
7. **RabbitMQ** http://localhost:15672 (`food` / `food_pass`) → Queues: у каждого сервиса своя очередь и `.dlq`.
8. **Swagger** http://localhost:8080/docs → любой сервис → Authorize.
9. **Трассировка**: `docker compose logs order-service --tail 20`, взять `request_id` и найти его во всех логах:
   `docker compose logs | findstr <request_id>`.
10. **Отказоустойчивость**:
    ```
    docker compose stop restaurant-service
    # клиент пытается оформить заказ → понятная ошибка 503 «Сервис restaurant-service недоступен»
    docker compose start restaurant-service

    docker compose stop notification-service
    # оформить и оплатить заказ — всё работает, уведомления копятся в очереди (видно в RabbitMQ UI)
    docker compose start notification-service
    # уведомления появляются в колокольчике
    ```
11. `pytest tests/e2e -v` — 7 сквозных сценариев; вкладка Actions на GitHub — зелёные проверки.

## Вероятные вопросы

**Чем микросервис отличается от модуля монолита?**
Отдельный процесс, отдельная база, отдельный Dockerfile и конфигурация. С другими общается только через API
или события; доступа к чужим таблицам нет. Можно перезапустить или масштабировать независимо.

**Почему 7 сервисов, а не 3?**
Каждый владеет своими данными и меняется по своим причинам. Отзывы и уведомления можно отключить — заказы
продолжат работать. Каталог ресторанов читают все, его можно масштабировать отдельно от оплаты.

**Почему одна PostgreSQL, если «database per service»?**
Сервер один, баз семь, у каждой свой пользователь, чужая база недоступна (`REVOKE CONNECT`). Логически изоляция
полная; это экономия ресурсов для учебного окружения. Разнести по серверам — поменять `DATABASE_URL`.

**Где синхронное взаимодействие и почему?**
Когда ответ нужен прямо сейчас: цены и наличие блюд при оформлении заказа, имя и телефон курьера, сверка при старте.
Всего 5 REST-связей, и цепочек длиннее одного шага нет.

**Что такое saga? Какие у вас компенсации?**
Последовательность локальных транзакций в разных сервисах, связанных событиями. Если шаг не удался — выполняется
компенсирующее действие: оплата не прошла (3 отказа или 15 минут) → заказ отменяется; ресторан отказался от
оплаченного заказа → payment-service возвращает деньги.

**Что будет, если упадёт RabbitMQ?**
API продолжают работать, `/ready` показывает `rabbitmq: fail`. События сохраняются в таблицах outbox и уйдут,
когда брокер вернётся (переподключение автоматическое).

**Что такое transactional outbox?**
Изменение (например, новый заказ) и событие о нём записываются в базу **одной транзакцией**. Отдельная фоновая
задача читает таблицу outbox и публикует события. Не бывает ситуации «заказ сохранён, а событие потерялось».

**Что если событие придёт дважды?**
Обработчики идемпотентны: платёж и доставка уникальны по `order_id`, уведомление — по `event_id` и получателю,
отзыв — один на заказ, повторная смена статуса заказа просто пропускается.

**Двое курьеров одновременно нажали «Взять заказ». Что будет?**
Взятие сделано одним атомарным запросом `UPDATE deliveries SET courier_id=... WHERE id=... AND status='searching'`.
Обновится ровно одна строка — у первого; второй получит `409 already_taken`. Это проверяется тестом.

**Клиент дважды нажал «Оформить заказ». Будет два заказа?**
Нет. Браузер отправляет заголовок `Idempotency-Key`; по нему order-service вернёт уже созданный заказ.

**Как работает авторизация?**
auth-service выдаёт JWT с id пользователя и ролью. Каждый сервис сам проверяет подпись и сам решает, можно ли
пользователю работать с его данными: заказ видят клиент, ресторан, назначенный курьер и админ; меню меняет только
владелец ресторана. Чужое возвращает 404, чтобы не раскрывать, что объект существует.

**Почему проверка JWT не на gateway?**
Иначе на каждый запрос нужно ходить в auth-service, а сервисы были бы открыты при обходе gateway.

**Как защищены внутренние endpoint'ы?**
Ключ `X-Internal-Key`. Gateway не проксирует `/internal/*` и затирает этот заголовок, если его прислал клиент.

**Как обрабатываются ошибки?**
Единый формат `{"error": {"code", "message", "request_id", "details"}}` во всех сервисах и в gateway; stack trace
только в логах. Ошибка соседнего сервиса пробрасывается с исходным кодом: «ресторан закрыт» доходит до клиента
как `409 restaurant_closed`. Недоступность соседа — `503`, таймаут — `504`.

**Что логируется и как найти запрос?**
JSON: timestamp, service, level, request_id, message + контекст (id заказа, статус, длительность).
`X-Request-ID` создаёт gateway, он передаётся в HTTP-вызовах и внутри событий RabbitMQ.

**Чем /health отличается от /ready?**
`/health` — процесс жив (если нет — перезапустить). `/ready` — доступны ли БД и брокер (если нет — не слать трафик).
В Kubernetes (ЛР3) это liveness и readiness probes.

**Как тестировали?**
60 unit-тестов — каждый сервис изолированно, соседи подменены (SQLite, in-memory шина событий, mock HTTP).
7 e2e-сценариев — вся система через gateway. GitHub Actions запускает тесты и собирает все Docker-образы на каждый push.

**Как масштабировать?**
restaurant, order, payment и review можно запускать в нескольких экземплярах: состояние в базе, события из одной
очереди RabbitMQ распределяются между экземплярами. Сложнее с payment-service (фоновая проверка просроченных
платежей): нужна блокировка в БД, чтобы её делал один экземпляр.

**Слабые места (лучше назвать самим):**
* схема БД создаётся `create_all` + автодобавление колонок — в продакшене нужен Alembic;
* JWT нельзя отозвать до истечения срока;
* есть только request_id, нет полноценного distributed tracing (OpenTelemetry + Jaeger);
* один сервер PostgreSQL, секреты в `.env`, а не в vault;
* платёжный шлюз — эмуляция.
